# 数据库迁移 V5 详细设计

> **版本**：V5  
> **目标版本**：V1.4（专家评审04后修订版）  
> **数据库**：SQLite（开发/测试）/ MySQL（生产）  
> **归属**：`dms-app/src/main/resources/db/migration/V5__v1_4_refactor.sql`  
> **DDL 归属模块**：`dms-production`（含 analytics 视图）
>
> **命名规范**：全局仅使用一个 V5 脚本文件，各模块的 DDL 合并到该文件中。
> 若后续 Flyway 化，统一版本号递增（V5 → V6），禁止同版本号多文件。

## 一、迁移概述

### 1.1 当前状态

| 项目 | 状态 |
|------|------|
| 数据库类型 | SQLite（单文件 `dms.db`），未来生产环境迁移至 MySQL |
| 迁移机制 | 自定义 `DatabaseInitConfig`（`CommandLineRunner`），非 Flyway |
| 已执行脚本 | `V1__init.sql` → `V2__refactor.sql` → `V3__new_flow.sql` → `V4__module_split.sql` |
| 当前数据 | `sys_config` 表为空；业务表无生产数据（0 条记录） |
| 基类现状 | 仅存在 `BaseEntity`（含 `deleted`），无 `BaseAuditEntity` |

### 1.2 迁移目标（V1.4）

本次迁移对应 V1.4 需求变更，共涉及 **6 大类操作**：

| # | 目标 | 涉及表 | 说明 |
|---|------|--------|------|
| 1 | BaseEntity/BaseAuditEntity 拆分 | `sys_log`、`eq_temperature_log`、`prod_task_status_history` | 审计类表去除 `deleted` 字段，实体改为继承 `BaseAuditEntity` |
| 2 | `prod_task` 字段精简 | `prod_task` | 删除 8 个冗余步骤时间字段，新增通用 `stage_start_time` |
| 3 | `md_decoct_scheme` 扩展 | `md_decoct_scheme` | 新增 `trace_code`、`alarm_high_temp`、`alarm_low_temp` |
| 4 | `prt_record` 扩展 | `prt_record` | 新增 `operator_id` |
| 5 | `sys_config` 初始化 | `sys_config` | 插入 6 条系统默认配置 |
| 6 | Analytics 视图创建 | `ops_daily_capacity`、`ops_equipment_utilization` | DDL 归属 `dms-production`，供 `dms-analytics` 只读查询 |

### 1.3 核心约束

- **SQLite 的 ALTER TABLE 限制**：不支持 `DROP COLUMN`，不支持 `ALTER COLUMN` 修改类型。删除列或修改类型必须**重建表**（`CREATE NEW` → `INSERT SELECT` → `DROP OLD` → `RENAME NEW`）。
- **外键约束**：`prod_task` 被 `prod_task_status_history`、`prod_step_log`、`prod_work_record`、`prod_handover_detail` 四个表以外键引用。重建 `prod_task` 时必须临时**关闭外键检查**或**按依赖顺序重建**。
- **幂等性**：脚本必须支持重复执行不报错（`IF NOT EXISTS`、`IF EXISTS`、条件判断）。
- **双版本 DDL**：每条结构性变更必须提供 SQLite 和 MySQL 两个版本。

## 二、迁移机制设计（自定义迁移 vs Flyway 对比，推荐方案）

### 2.1 当前机制：DatabaseInitConfig（自定义）

```java
// 当前实现：cn.org.openygt.config.DatabaseInitConfig
@Component
public class DatabaseInitConfig implements CommandLineRunner {
    private static final String[] SCRIPTS = {
        "V1__init.sql",
        "V2__refactor.sql",
        "V3__new_flow.sql",
        "V4__module_split.sql"
    };
    // ... 使用 sys_migration 表记录已执行脚本
}
```

**优点**：
- 零依赖，不引入 Flyway 等第三方库；
- 与 Spring Boot 生命周期天然集成；
- 适合 SQLite 这种轻量级场景。

**缺点**：
- 手写 `hasRun` / `markRun` 逻辑，存在 SQL 注入风险（当前用字符串拼接 `script` 名）；
- 无 Flyway 的 checksum 校验，脚本被篡改后无法发现；
- 无 Flyway 的占位符（`${placeholder}`）支持，双环境（SQLite/MySQL）脚本分离成本高；
- 回滚需手动写逆向脚本，无自动回滚能力。

### 2.2 对比：Flyway

| 维度 | DatabaseInitConfig（当前） | Flyway（推荐） |
|------|---------------------------|---------------|
| 依赖 | 零第三方依赖 | `flyway-core`（约 200KB） |
| SQL 注入风险 | **高**（字符串拼接 script 名） | 低（内部使用 PreparedStatement） |
| 幂等/版本控制 | 手工维护 `sys_migration` | 自动维护 `flyway_schema_history` |
| Checksum 校验 | ❌ 无 | ✅ 有 |
| 占位符/多环境 | ❌ 需手写两套脚本 | ✅ `${vendor}` 等占位符 |
| SQLite 支持 | ✅ 原生支持 | ✅ 社区版支持 |
| 团队熟悉度 | 仅本项目使用 | 业界标准 |

### 2.3 推荐方案：两阶段演进

**阶段一（V5 本次）：保留自定义迁移，但修复安全漏洞**

理由：
- 项目当前处于快速迭代期，引入 Flyway 需额外配置与测试；
- 自定义迁移已跑通 V1~V4，机制本身可用；
- 本次核心任务是**修复 SQL 注入** + **补全 V5 脚本**。

**阶段二（V6 或生产发布前）：迁移至 Flyway**

理由：
- 生产环境使用 MySQL，Flyway 对 MySQL 支持最为成熟；
- Flyway 的 ` repeatable migration` 适合 analytics 视图的频繁变更；
- checksum 机制可防止部署包被篡改后静默执行错误脚本。

**V5 折中方案**：
- 保持 `DatabaseInitConfig` 框架不变；
- 将 `hasRun` / `markRun` 中的字符串拼接改为 `PreparedStatement`；
- 新增 `V5__v1_4_refactor.sql` 到脚本列表；
- 脚本内部通过 SQLite/MySQL 特有的条件注释实现双版本兼容（或分两个文件由配置切换）。

## 三、DatabaseInitConfig 安全修复（PreparedStatement 替代字符串拼接）

### 3.1 当前漏洞代码

```java
// dms-app/src/main/java/cn/org/openygt/config/DatabaseInitConfig.java
private boolean hasRun(Connection conn, String script) throws Exception {
    try (Statement stmt = conn.createStatement();
         ResultSet rs = stmt.executeQuery(
             "SELECT COUNT(*) FROM sys_migration WHERE script = '" + script + "'")) {
        return rs.next() && rs.getInt(1) > 0;
    }
}

private void markRun(Connection conn, String script) throws Exception {
    try (Statement stmt = conn.createStatement()) {
        stmt.execute("INSERT INTO sys_migration (script) VALUES ('" + script + "')");
    }
}
```

**风险**：`script` 参数虽来自内部常量数组，但若未来被外部化配置（如从 `application.yml` 读取），存在注入风险。应遵循**纵深防御**原则。

### 3.2 修复后代码

```java
package cn.org.openygt.config;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.boot.CommandLineRunner;
import org.springframework.core.io.ClassPathResource;
import org.springframework.jdbc.datasource.init.ScriptUtils;
import org.springframework.stereotype.Component;

import javax.sql.DataSource;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.Statement;

@Component
public class DatabaseInitConfig implements CommandLineRunner {

    private static final Logger log = LoggerFactory.getLogger(DatabaseInitConfig.class);

    private static final String[] SCRIPTS = {
        "V1__init.sql",
        "V2__refactor.sql",
        "V3__new_flow.sql",
        "V4__module_split.sql",
        "V5__v1_4_refactor.sql"   // ✅ V5 新增
    };

    private final DataSource dataSource;

    public DatabaseInitConfig(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    @Override
    public void run(String... args) throws Exception {
        try (Connection conn = dataSource.getConnection()) {
            ensureMigrationTable(conn);
            for (String script : SCRIPTS) {
                if (!hasRun(conn, script)) {
                    log.info("执行迁移脚本: {}", script);
                    ScriptUtils.executeSqlScript(conn, new ClassPathResource("db/migration/" + script));
                    markRun(conn, script);
                } else {
                    log.info("跳过已执行脚本: {}", script);
                }
            }
        }
    }

    private void ensureMigrationTable(Connection conn) throws Exception {
        String ddl = conn.getMetaData().getDatabaseProductName().toLowerCase().contains("mysql")
            ? "CREATE TABLE IF NOT EXISTS sys_migration ("
                + "id BIGINT PRIMARY KEY AUTO_INCREMENT,"
                + "script VARCHAR(100) NOT NULL UNIQUE,"
                + "executed_at DATETIME DEFAULT CURRENT_TIMESTAMP)"
            : "CREATE TABLE IF NOT EXISTS sys_migration ("
                + "id INTEGER PRIMARY KEY AUTOINCREMENT,"
                + "script VARCHAR(100) NOT NULL UNIQUE,"
                + "executed_at DATETIME DEFAULT CURRENT_TIMESTAMP)";
        try (Statement stmt = conn.createStatement()) {
            stmt.execute(ddl);
        }
    }

    // ✅ 修复：使用 PreparedStatement 防止 SQL 注入
    private boolean hasRun(Connection conn, String script) throws Exception {
        String sql = "SELECT COUNT(*) FROM sys_migration WHERE script = ?";
        try (PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setString(1, script);
            try (ResultSet rs = ps.executeQuery()) {
                return rs.next() && rs.getInt(1) > 0;
            }
        }
    }

    // ✅ 修复：使用 PreparedStatement 防止 SQL 注入
    private void markRun(Connection conn, String script) throws Exception {
        String sql = "INSERT INTO sys_migration (script) VALUES (?)";
        try (PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setString(1, script);
            ps.executeUpdate();
        }
    }
}
```

### 3.3 修复要点说明

| 方法 | 修复前 | 修复后 | 效果 |
|------|--------|--------|------|
| `hasRun` | `Statement` + 字符串拼接 | `PreparedStatement` + `?` 占位符 | 杜绝注入，即使 `script` 来自外部配置也安全 |
| `markRun` | `Statement` + 字符串拼接 | `PreparedStatement` + `?` 占位符 | 同上 |
| `ensureMigrationTable` | 硬编码 SQLite 语法（`AUTOINCREMENT`） | 根据 `DatabaseMetaData` 自动判断 MySQL/SQLite | 兼容双环境 |

## 四、V5 迁移脚本详细设计（SQLite 版 + MySQL 版，逐表说明）

> 脚本文件：`dms-app/src/main/resources/db/migration/V5__v1_4_refactor.sql`

### 4.0 前置公共语句（双版本）

```sql
-- ============================================
-- 公共前置：关闭外键检查（SQLite 重建表需要）
-- ============================================

-- 【SQLite】
PRAGMA foreign_keys = OFF;

-- 【MySQL】
-- SET FOREIGN_KEY_CHECKS = 0;
-- 注：MySQL 因支持 DROP COLUMN，通常不需要关闭外键。仅在极端情况下使用。
```

> **差异说明**：SQLite 重建被外键引用的父表时，必须关闭外键检查，否则 `DROP TABLE` 失败。MySQL 支持 `DROP COLUMN`，无需重建表，因此无需关闭外键。

---

### 4.1 sys_log —— 去除 deleted 字段（审计表规范化）

**现状**：V4 创建的 `sys_log` **本无 `deleted` 字段**，但为防某些开发/测试环境被误加，脚本需幂等处理。

**目标**：确保 `sys_log` 无 `deleted` 字段，无 `updated_at` 字段，符合 `BaseAuditEntity`（仅 `id, tenant_id, created_at, updated_at`）。

> 注：当前 `sys_log` 的 DDL 为 `id, tenant_id, user_id, action, module, detail, ip_address, created_at`，已符合审计表规范（无 `deleted`）。本次脚本以**幂等确认**为主。

```sql
-- ============================================
-- 4.1 sys_log：确保无 deleted 字段（幂等）
-- ============================================

-- 【SQLite】
-- SQLite 不支持 DROP COLUMN。若存在 deleted，需重建表。
-- 由于当前 sys_log 本无 deleted，以下重建脚本仅为防御性设计。
CREATE TABLE IF NOT EXISTS sys_log_new (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    tenant_id VARCHAR(32) DEFAULT 'default',
    user_id VARCHAR(50),
    action VARCHAR(100) NOT NULL,
    module VARCHAR(50) NOT NULL,
    detail TEXT,
    ip_address VARCHAR(50),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
INSERT INTO sys_log_new SELECT id, tenant_id, user_id, action, module, detail, ip_address, created_at FROM sys_log;
DROP TABLE IF EXISTS sys_log;
ALTER TABLE sys_log_new RENAME TO sys_log;
CREATE INDEX IF NOT EXISTS idx_sys_log_user ON sys_log(user_id);
CREATE INDEX IF NOT EXISTS idx_sys_log_module ON sys_log(module);
CREATE INDEX IF NOT EXISTS idx_sys_log_created ON sys_log(created_at);

-- 【MySQL】
-- MySQL 8.0.3+ 支持 ALTER TABLE ... DROP COLUMN
-- 由于当前 sys_log 本无 deleted，以下语句执行时若列不存在会报错，需用存储过程或忽略错误。
-- 推荐方案：在应用层 Entity（SysLog）中去掉 @TableLogic，不强制改 DDL。
-- 若确需清理误加的 deleted 列：
-- SET @col_exists = (SELECT COUNT(*) FROM information_schema.columns 
--                    WHERE table_name = 'sys_log' AND column_name = 'deleted' AND table_schema = DATABASE());
-- SET @sql = IF(@col_exists > 0, 'ALTER TABLE sys_log DROP COLUMN deleted', 'SELECT 1');
-- PREPARE stmt FROM @sql; EXECUTE stmt; DEALLOCATE PREPARE stmt;
```

> **差异说明**：
> - SQLite 无 `IF EXISTS` 的 `DROP COLUMN`，必须重建表。
> - MySQL 8.0.3+ 支持 `DROP COLUMN IF EXISTS`，但旧版不支持。最安全的做法是在 Entity 层规范（继承 `BaseAuditEntity`，不含 `deleted`），数据库层保持现状。

### 4.4 prod_task —— 字段精简（核心变更）

**现状字段**：
`id, prescription_id, decoct_device_id, package_device_id, scheme_id, operator_id, status, current_temp, target_temp, soak_duration, soak_start_time, soak_end_time, decoct_start_time, decoct_end_time, pour_start_time, pour_end_time, wrap_start_time, wrap_end_time, complete_time, current_stage_duration, print_device_id, print_status, print_time, deleted, created_at, updated_at, current_step, pool_id, print_copies, is_exception, exception_reason, patient_agreement, standard_cost, actual_cost, handover_type, handover_user, handover_time, tenant_id`

**目标字段**（删除 8 个冗余字段，新增 1 个通用字段）：
- ❌ 删除：`soak_start_time`, `soak_end_time`, `decoct_start_time`, `decoct_end_time`, `pour_start_time`, `pour_end_time`, `wrap_start_time`, `wrap_end_time`
- ✅ 新增：`stage_start_time` DATETIME
- ✅ 保留：其余所有字段（含 `deleted`，因为 `Task` 仍继承 `BaseEntity`）

> **业务解释**：各步骤的开始/结束时间已完整记录在 `prod_step_log`（`started_at` / `ended_at`），`prod_task` 只需保留当前阶段开始时间 `stage_start_time` 和完成时间 `complete_time`。

## 五、数据迁移策略（prod_task 字段迁移到 step_log 的补偿逻辑）

### 5.1 问题背景

`prod_task` 删除的 8 个字段（`soak_start_time` ~ `wrap_end_time`）在部分测试/演示环境中可能已有历史数据。直接删除会导致**历史步骤时间丢失**。

### 5.2 补偿逻辑设计

**原则**：被删除的字段数据应已存在于 `prod_step_log`，但若 `prod_step_log` 缺失（如早期版本未记录），需在迁移前将 `prod_task` 的旧字段回填到 `prod_step_log`。

#### 5.2.1 补偿脚本（迁移前执行）

```sql
-- ============================================
-- prod_task → prod_step_log 历史数据补偿
-- 执行时机：在 prod_task 重建/删列 **之前**
-- ============================================

-- 【SQLite / MySQL 通用】
-- 将 prod_task 中各阶段时间插入到 prod_step_log（若该阶段不存在记录）

-- 1. 泡药阶段 SOAK
INSERT INTO prod_step_log (task_id, step_type, device_id, operator_id, started_at, ended_at, result, created_at, updated_at, tenant_id)
SELECT
    pt.id,
    'SOAK',
    NULL,
    pt.operator_id,
    pt.soak_start_time,
    pt.soak_end_time,
    '正常',
    COALESCE(pt.soak_start_time, pt.created_at),
    COALESCE(pt.soak_end_time, pt.updated_at),
    pt.tenant_id
FROM prod_task pt
LEFT JOIN prod_step_log psl ON pt.id = psl.task_id AND psl.step_type = 'SOAK'
WHERE pt.soak_start_time IS NOT NULL
  AND psl.id IS NULL;  -- 仅当 step_log 中无 SOAK 记录时才补偿

    pt.id,

    pt.decoct_device_id,
    pt.operator_id,
    pt.decoct_start_time,
    pt.decoct_end_time,
    '正常',
    COALESCE(pt.decoct_start_time, pt.created_at),
    COALESCE(pt.decoct_end_time, pt.updated_at),
    pt.tenant_id
FROM prod_task pt
LEFT JOIN prod_step_log psl ON pt.id = psl.task_id AND psl.step_type = 'DECOCT'

  AND psl.id IS NULL;

-- 3. 出液阶段 POUR
INSERT INTO prod_step_log (task_id, step_type, device_id, operator_id, started_at, ended_at, result, created_at, updated_at, tenant_id)

    pt.id,

    pt.decoct_device_id,
    pt.operator_id,

    COALESCE(pt.pour_start_time, pt.created_at),

### 7.1 ops_daily_capacity（日产能统计视图）

**口径**：按日统计任务总数、已完成数、已报废数。

```sql
-- ============================================
-- 7.1 ops_daily_capacity 视图
-- ============================================

-- 【SQLite】
CREATE VIEW IF NOT EXISTS ops_daily_capacity AS
SELECT
    DATE(created_at) AS stat_date,
    tenant_id,
    COUNT(*) AS total_tasks,
    SUM(CASE WHEN status = '已完成' THEN 1 ELSE 0 END) AS completed_tasks,
    SUM(CASE WHEN status = '已报废' THEN 1 ELSE 0 END) AS scrapped_tasks,
    SUM(CASE WHEN status NOT IN ('已完成', '已报废', '已取消') THEN 1 ELSE 0 END) AS in_progress_tasks
FROM prod_task
WHERE deleted = 0
GROUP BY DATE(created_at), tenant_id;

-- 【MySQL】
CREATE OR REPLACE VIEW ops_daily_capacity AS
SELECT
    DATE(created_at) AS stat_date,
    tenant_id,
    COUNT(*) AS total_tasks,
    SUM(CASE WHEN status = '已完成' THEN 1 ELSE 0 END) AS completed_tasks,
    SUM(CASE WHEN status = '已报废' THEN 1 ELSE 0 END) AS scrapped_tasks,
    SUM(CASE WHEN status NOT IN ('已完成', '已报废', '已取消') THEN 1 ELSE 0 END) AS in_progress_tasks
FROM prod_task
WHERE deleted = 0
GROUP BY DATE(created_at), tenant_id;
```

> **状态值说明**：当前版本数据库存储中文状态值（与代码中 `TaskStatus.getLabel()` 一致）。
> 后续迭代（V6）将统一迁移为枚举名（`COMPLETED`/`SCRAPPED`/`PARTIAL_COMPLETED` 等），届时同步更新视图定义。
```

> **差异说明**：
> - SQLite 使用 `CREATE VIEW IF NOT EXISTS`，重复执行不报错。
> - MySQL 使用 `CREATE OR REPLACE VIEW`，可更新视图定义。

### 7.2 ops_equipment_utilization（设备利用率视图）

**口径**：按设备和日期统计煎药/包装的运行时长（分钟）。

```sql
-- ============================================
-- 7.2 ops_equipment_utilization 视图
-- ============================================

-- 【SQLite】
-- SQLite 无 TIMESTAMPDIFF，使用 julianday 差值换算分钟
CREATE VIEW IF NOT EXISTS ops_equipment_utilization AS
SELECT
    device_id,
    DATE(started_at) AS stat_date,
    step_type,
    SUM(
        CASE
            WHEN ended_at IS NOT NULL THEN CAST((julianday(ended_at) - julianday(started_at)) * 1440 AS INTEGER)
            ELSE 0
        END
    ) AS running_minutes,
    COUNT(*) AS step_count
FROM prod_step_log
WHERE step_type IN ('DECOCT', 'WRAP')
  AND deleted = 0
GROUP BY device_id, DATE(started_at), step_type;

-- 【MySQL】
-- MySQL 使用 TIMESTAMPDIFF(MINUTE, start, end)
CREATE OR REPLACE VIEW ops_equipment_utilization AS
SELECT
    device_id,
    DATE(started_at) AS stat_date,
    step_type,
    SUM(
        CASE
            WHEN ended_at IS NOT NULL THEN TIMESTAMPDIFF(MINUTE, started_at, ended_at)
            ELSE 0
        END
    ) AS running_minutes,
    COUNT(*) AS step_count
FROM prod_step_log
WHERE step_type IN ('DECOCT', 'WRAP')
  AND deleted = 0
GROUP BY device_id, DATE(started_at), step_type;
```

> **差异说明**：
> - **时间差函数**：SQLite 用 `(julianday(end) - julianday(start)) * 1440`；MySQL 用 `TIMESTAMPDIFF(MINUTE, start, end)`。
> - **类型转换**：SQLite 的 `julianday` 返回浮点数，需 `CAST(... AS INTEGER)` 取整分钟。
> - **NULL 处理**：两段脚本均通过 `CASE WHEN ended_at IS NOT NULL` 避免未结束步骤被计入。

- SQLite 为文件数据库，**回滚最佳实践是文件级备份**（复制 `dms.db`）。

### 8.3 回滚脚本（SQLite 版）

SQLite 不支持 `DROP COLUMN`，回滚成本极高，**强烈建议执行前备份 `dms.db` 文件**。

```bash
# SQLite 回滚最佳实践：文件级备份/恢复
# 执行 V5 前：
cp dms.db dms.db.v4.backup

# 需要回滚时：
cp dms.db.v4.backup dms.db
```

若必须脚本回滚，需再次**重建所有被修改的表**，复杂度与正向迁移相同，此处省略。
