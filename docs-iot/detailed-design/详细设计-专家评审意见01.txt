  这意味着：      
  - 每个需要认证的 Controller 方法都必须手动调用 requireLogin(request)
  - 任何遗漏的 Controller 方法都会成为无认证的裸露接口

  修订建议：Filter 层应对非白名单 URL 在 Token 校验失败时直接返回 401，不放行到 Controller。白名单路径在 Filter 的 shouldNotFilter() 中排除：  
                                                                                                                                               
  @Override                                                                                                                                    
  protected boolean shouldNotFilter(HttpServletRequest request) {                                                                              
      String path = request.getRequestURI();                                                                                                   
      return path.startsWith("/api/v1/sys/auth/login")
          || path.startsWith("/health")                                                                                                        
          || path.startsWith("/actuator");
  }                                                                                                                                            
                  
  非白名单且 Token 无效时：                                                                                                                    
  response.setStatus(HttpServletResponse.SC_UNAUTHORIZED);

  return; // 不调用 filterChain.doFilter

  七、数据库迁移审核补充
                                                                                                                                               
  21. V5 迁移脚本的 SQLite INSERT INTO ... SELECT 在表重建时可能丢失列
                                                                                                                                               
  数据库迁移-V5-详细设计.md 第 628-633 行 prod_step_log 重建：                                                                                 
                                                                                                                                               
  INSERT INTO prod_step_log_new SELECT * FROM prod_step_log;                                                                                   
                                                                                                                                               
  问题：SELECT * 依赖列的位置顺序。如果新旧表的列数或列顺序不同（新表新增了 device_id 类型变更，可能导致列顺序变化），SELECT *                 
  会导致数据错位或插入失败。                                                                                                                   
                                                                                                                                               
  修订：所有 INSERT INTO ... SELECT 必须显式列出列名（与第 447-466 行 prod_task 的正确做法一致）：                                             
   
  INSERT INTO prod_step_log_new (id, tenant_id, task_id, parent_id, step_type, device_id, ...)                                                 
  SELECT id, tenant_id, task_id, parent_id, step_type, CAST(device_id AS INTEGER), ...                                                         
  FROM prod_step_log;                                                                                                                          
                                                                                                                                               
  22. V5 脚本未处理 prt_task.max_retry 新增列                                                                                                  
                  
  数据库迁移-V5-详细设计.md 涵盖了 sys_log、eq_temperature_log、prod_task_status_history、prod_task、md_decoct_scheme、prt_record              
  的迁移，但遗漏了 prt_task 表新增 max_retry 列的 DDL。dms-print-详细设计.md 第 1369-1370 行提到需要执行：
                                                                                                                                               
  ALTER TABLE prt_task ADD COLUMN max_retry INTEGER DEFAULT 3;
                                                                                                                                               
  但这段 DDL 未出现在 V5 统一迁移脚本中。                                                                                                      
                                                                                                                                               
  修订：在 V5__v1_4_refactor.sql 中补充 prt_task.max_retry 和 prt_record.printer_code 的增量 DDL（dms-print-详细设计.md 第 1373 行）。

  八、测试策略审核
                  
  23. dms-production 的悲观锁并发测试在 H2 上不可靠
                                                                                                                                               
  dms-production-详细设计.md 第 1816-1852 行的并发设备绑定测试使用多线程验证 SELECT FOR UPDATE。但测试配置（第 1692 行）标注使用 H2            
  内存数据库。H2 的 FOR UPDATE 行为与 MySQL/SQLite 差异显著——H2 默认使用 MVCC，FOR UPDATE 不一定能阻塞并发读取。                               
                                                                                                                                               
  修订：悲观锁并发测试必须标注为集成测试，使用 @SpringBootTest + Testcontainers MySQL 容器（或真实 SQLite 文件），不能依赖 H2 验证锁行为。在 H2
   环境下的单元测试仅验证 SQL 语法正确性和业务逻辑，不验证并发排斥效果。
                                                                                                                                               
  24. dms-quality 的测试缺少 InspectionSummaryDTO/InspectionTrendDTO 的序列化定义                                                              
   
  dms-quality-详细设计.md 第 485-494 行的 getInspectionSummary 和 getInspectionTrend 返回 InspectionSummaryDTO 和                              
  List<InspectionTrendDTO>，但这两个 DTO 的定义位置不明确——第 661-701 行在文档内定义了它们，但没有说明放在 dms-common.dto 还是
  dms-quality.dto。如果放在 dms-quality，则 dms-common.QualityService 接口无法引用它们（循环依赖）。                                           
                  
  修订：InspectionSummaryDTO 和 InspectionTrendDTO 必须放在 dms-common.dto 包中（与 CapacityDailyDTO 同级），因为它们是 SPI                    
  接口的返回类型。同时补充到 dms-common-详细设计.md 的 DTO 总览表中。
