## 一、项目全景

### 1.1 项目名称与定位

- **项目名称**：openygt-dms（煎药室数字化管理系统）
- **业务定位**：覆盖医院煎药中心从处方接收、泡药、煎药、出液、包装、贴标、质检到交接的完整 12 步生产流程，支持多厂商煎药机/包装机 IoT 接入。
- **部署形态**：模块化单体应用（Modular Monolith），单 JAR 部署，端口 8080。

## 二、整体架构原则

### 2.1 模块化单体约束

1. **单 JVM 运行**：所有模块最终打包为同一个 Spring Boot JAR，由 `dms-app` 统一启动。
2. **同进程调用**：模块间通信**禁止**使用 Feign、MQ、EventBus 等远程/异步机制，统一采用 `dms-common` 定义 SPI 接口 + Spring 依赖注入。
3. **数据库共享**：所有模块共享同一 SQLite 文件（单库），通过**表前缀**逻辑隔离。
4. **禁止跨模块数据访问**：
   - ✅ 允许：通过 `dms-common` 的 SPI 接口调用其他模块服务
   - ❌ 禁止：直接 `import` 其他模块的 Mapper、Entity、ServiceImpl
   - ❌ 禁止：直接操作其他模块的数据库表（除非通过 SPI）

### 2.2 包名规范

统一根包：`cn.org.openygt`

```
cn.org.openygt
├── common/          # dms-common
├── masterdata/      # dms-masterdata
├── system/          # dms-system
├── equipment/       # dms-equipment
├── production/      # dms-production
├── quality/         # dms-quality
├── print/           # dms-print
└── analytics/       # dms-analytics
```

### 2.3 数据库规范

- **业务表**继承 `BaseEntity`（含逻辑删除），包含：`id`, `tenant_id`, `created_at`, `updated_at`, `deleted`
- **审计/遥测表**继承 `BaseAuditEntity`（**不含逻辑删除**），包含：`id`, `tenant_id`, `created_at`, `updated_at`
  - 适用表：`sys_log`、`eq_temperature_log`、`eq_temperature_log_archive`、`prod_task_status_history`
- **逻辑删除**：全局启用，`deleted = 1` 表示已删除，`0` 表示正常。审计数据**禁止逻辑删除**。
- **表前缀**：必须与模块名一致（`md_`, `sys_`, `eq_`, `prod_`, `qt_`, `prt_`）
- **外键约束**：SQLite 层面保留外键，但应用层逻辑删除时需自行处理级联
- **多租户**：预留 `tenant_id` 字段，当前全为 `'default'`
- **多租户排除表**：`sys_log`、`eq_temperature_log`、`eq_temperature_log_archive`、`prod_task_status_history` 等审计表在 `TenantLineInnerInterceptor` 中明确排除，避免归档查询和跨租户审计被拦截

### 2.4 API 规范

- **Base URL**：`http://localhost:8080`
- **版本前缀**：`/api/v1`
- **模块前缀**：`/{模块缩写}`，例如 `/api/v1/prod/tasks`
- **响应格式**：统一使用 `ApiResponse<T>` 包装
- **认证要求**：**所有API（除登录/健康检查外）必须携带JWT Token**，`Authorization: Bearer {token}`
- **传输层**：生产环境必须启用TLS（HTTPS）

### 2.5 错误码规范

| 模块 | 码段 | 示例 |
|------|------|------|
| 通用 / 系统 | `0000` ~ `0999` | `0000` 成功，`0001` 参数错误，`0002` 未授权 |
| dms-production | `1000` ~ `1999` | `1001` 状态非法，`1002` 设备被占用，`1003` 超时告警 |
| dms-equipment | `2000` ~ `2999` | `2001` 设备离线，`2002` 协议解析失败，`2003` 温度超限 |
| dms-quality | `3000` ~ `3999` | `3001` 质检结果非法 |
| dms-print | `4000` ~ `4999` | `4001` 打印失败，`4002` 重试次数超限 |
| dms-masterdata | `5000` ~ `5999` | `5001` 医院编码重复，`5002` 方案编码重复 |
| dms-system | `6000` ~ `6999` | `6001` 用户名密码错误，`6002` Token过期 |
| dms-analytics | `7000` ~ `7999` | `7001` 统计范围过大 |

- `code = 200` 仅表示 HTTP 层成功，业务错误使用上述码段
- 各模块在 `dms-common.exception` 中定义专属 `ErrorCode` 枚举

```json
{
  "code": 200,
  "message": "success",
  "data": { ... }
}
```

## 三、模块间接口契约（SPI）

三个跨模块服务接口定义在 `dms-common` 中，由对应模块实现，其他模块通过 `@Autowired` 注入使用。

> **调用方**：`dms-production`（核心）、`dms-print`

| 方法 | 职责 | 返回值 |
|------|------|--------|
| `getDeviceByCode(String)` | 按编码查询设备 | `EqDeviceDTO` |

| `getOrCreateDevice(String, int)` | 自动创建设备（首次扫码） | `EqDeviceDTO` |
| `updateDeviceStatus(Long, String)` | 更新设备状态（idle/running/fault/offline） | void |
| `updateTemperature(Long, BigDecimal)` | 更新设备实时温度 | void |
| `reportFault(Long, String, String)` | 上报设备故障 | void |
| `clearFault(Long)` | 清除故障 | void |
| `releaseDevice(Long)` | 释放设备（任务结束，状态置 idle） | void |

## 四、核心状态机（全局统一）

生产任务 `prod_task` 的状态流转是系统的核心，所有模块必须严格遵循以下状态定义：

```
待泡药(WAIT_SOAK)
    ↓ startSoak
泡药中(SOAKING)
    ↓ endSoak / 超时自动推进
待煎药(WAIT_DECOCT)
    ↓ startDecoct / 温度上报自动推进
煎药中(DECOCTING)
    ↓ endDecoct
待出液(WAIT_POUR)
    ↓ startPour / auto级设备自动推进
出液中(POURING)
    ↓ endPour / auto级设备自动推进
待包装(WAIT_WRAP)
    ↓ startWrap
包装中(WRAPPING)
    ↓ endWrap
待贴标(WAIT_LABEL)
    ↓ confirmLabel
待质检(WAIT_QC)
    ↓ qualityInspect
    ├─ 通过 → 待交接
    ├─ 让步放行 → 待交接（标记异常）
    ├─ 返工 → 待煎药
    └─ 报废 → 已报废(SCRAPPED)
待交接(WAIT_HANDOVER)
    ↓ handover
    ├─ 非最终 → 已部分完成(PARTIAL_COMPLETED)
    └─ 最终 → 已完成(COMPLETED)
```

**关键约束**：
- 状态流转必须通过 `TaskService` 的核心方法完成，禁止直接 UPDATE 数据库修改状态。
- 每次状态变更必须写入 `prod_task_status_history`。
- 每个工序阶段必须写入 `prod_step_log`。

## 九、风险与注意事项

1. **SQLite → MySQL 迁移风险**：生产环境必须切换至 MySQL，需验证数据类型兼容性（如 SQLite 的 `AUTOINCREMENT` 与 MySQL 的 `AUTO_INCREMENT`）、Flyway 脚本双版本、以及温度日志高频写入场景下 MySQL 的并发性能。
2. **东华原协议文档获取不确定性**：MVP 依赖东华原 TCP 二进制协议文档，若厂商无法及时提供，需准备抓包分析预案（Wireshark + 模拟器对比），可能延误 1-2 周。
3. **MQTT 消息可靠性**：当前 MQTT 客户端为 Paho 同步模式，设备指令下发需考虑超时、重试、幂等性设计。
4. **多租户拦截器与审计表冲突**：`TenantLineInnerInterceptor` 若配置遗漏排除审计表，会导致归档查询和跨租户审计被错误拦截，需在配置类中显式声明排除清单并加单元测试验证。
5. **设备适配器协议差异**：不同厂商的 MQTT/TCP 报文格式差异大，适配器框架的抽象程度需在实际接入中验证，存在框架返工风险。
