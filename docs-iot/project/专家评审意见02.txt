● 全部文档已读完。以下是我作为架构师的修订意见，按严重程度分层。

  一、致命级问题（必须修正，否则系统无法正确运行）                                                                                             
                                                                                                                                               
  1. dms-analytics 直接跨模块读表，违反自身架构原则                                                                                            
                                                                                                                                               
  集成开发总计划.md 第 2.1 节明确规定"禁止跨模块数据访问"，但 dms-analytics 的 AnalyticsMapper 直接 SELECT 了                                  
  prod_task、eq_device_alarm、qt_inspection
  等其他模块的表。这不是"只读就没问题"——它建立了对其他模块表结构的编译期依赖，任何表结构变更都会静默破坏报表。                                 
                  
  修订建议：
  - 方案A（推荐）：在 dms-common 中为 analytics 定义只读 SPI 接口（如 ProductionQueryService.getDailyCapacity()），由各模块实现，analytics 通过
   SPI 获取数据                                                                                                                                
  - 方案B（折中）：如果坚持用 SQL 视图，视图的 DDL 应归属数据源模块维护（prod_task 的视图由 dms-production 的 Flyway 脚本创建），analytics
  只读视图                                                                                                                                     
                  
  2. PrintService.getPrintQueue() 返回 Object

  dms-common 中 PrintService 的 getPrintQueue() 返回 Object，这与专家评审"SPI 返回值从 Object 改为明确类型"的结论矛盾。EquipmentService
  已经修正为 EqDeviceDTO，但 PrintService 遗漏了。

  修订建议：定义 PrintTaskDTO 放入 dms-common.dto，返回 List<PrintTaskDTO>。

  3. QualityService 缺少 TaskQueryService SPI 反向查询能力                                                                                     
   
  dms-quality 删除了内部的 Task.java 和 TaskMapper.java（正确），但质检报表（QT-003）需要关联 prod_task 的医院、方案等信息做统计。文档说"通过  
  SPI 或 REST API 获取"，但 dms-common 中并没有定义 TaskQueryService 或 ProductionService SPI 接口供 quality 反查任务信息。
                                                                                                                                               
  修订建议：在 dms-common 中新增 ProductionQueryService SPI：
  public interface ProductionQueryService {
      ProdTaskDTO getTaskById(Long taskId);
      List<ProdTaskDTO> getTasksByIds(List<Long> taskIds);
  }                                                       
   
  4. 状态机 startDecoct 代码示例仍保留 synchronized
                                                                                                                                               
  dms-production 第八节开发规范第 3 条，代码示例中方法签名仍然是 public synchronized Task startDecoct(...)，与"禁止继续使用
  synchronized"的文字要求自相矛盾。                                                                                                            
                  
  修订建议：删除示例中的 synchronized 关键字，改为纯数据库悲观锁示例。

  二、高危问题（影响模块边界完整性或数据一致性）
                                                                                                                                               
  5. eq_temperature_log 取消逻辑删除后，仍继承 BaseEntity
                                                                                                                                               
  文档明确说温度日志取消逻辑删除（物理保留+归档），但 BaseEntity 强制包含 deleted 字段和 @TableLogic 注解。如果实体仍继承                      
  BaseEntity，MyBatis-Plus 会自动在所有查询中追加 WHERE deleted = 0，导致归档后的数据无法正常查询。                                            
                                                                                                                                               
  修订建议：      
  - 方案A：EqTemperatureLog 不继承 BaseEntity，独立定义字段（推荐）
  - 方案B：BaseEntity 拆分为 BaseEntity（含逻辑删除）和 BaseAuditEntity（不含逻辑删除），温度日志继承后者
  - 同理，sys_log 也不做逻辑删除，需要同样处理

  6. prod_task_status_history 不应逻辑删除

  状态变更历史是审计数据，与温度日志同理，不应有 deleted 字段。但当前表设计中包含 deleted INTEGER DEFAULT
  0。审计数据一旦被逻辑删除，状态机的完整性追溯就断了。

  修订建议：prod_task_status_history 取消 deleted 字段，不继承 BaseEntity，或使用上述 BaseAuditEntity。                                        
   
  7. prod_step_log.device_id 类型不一致                                                                                                        
                  
  prod_step_log 表中 device_id 定义为 VARCHAR(50)（存设备编码），但 prod_task 中 decoct_device_id 是 INTEGER（存设备                           
  ID）。同一个"设备"概念在同一模块内用了两种标识方式，查询关联时需要额外转换。

  修订建议：统一为 INTEGER 类型存设备 ID，或统一为 VARCHAR 存设备编码。推荐统一用 Long deviceId，与 EquipmentService SPI 的参数类型一致。

  8. 多租户拦截器与 sys_log / eq_temperature_log 冲突

  TenantLineInnerInterceptor 会自动给所有查询追加 WHERE tenant_id = ?。但 sys_log 和 eq_temperature_log                                        
  这类审计/遥测表如果也被拦截，归档查询和跨租户审计会出问题。
                                                                                                                                               
  修订建议：在多租户拦截器配置中，明确排除 sys_log、eq_temperature_log、eq_temperature_log_archive、prod_task_status_history                   
  等审计表。文档中应列出排除清单。

  三、中危问题（影响可维护性或一致性）
                                      
  9. SPI 接口缺少异常契约
                                                                                                                                               
  三个 SPI 接口（EquipmentService、PrintService、QualityService）都没有定义异常行为。比如 getDeviceByCode 找不到设备时，是返回 null 还是抛     
  IllegalArgumentException？reserveDevice 设备已被预留时抛什么异常？                                                                           
                                                                                                                                               
  修订建议：在 dms-common 的 SPI 接口 Javadoc 中明确每个方法的异常契约：
  - 查询方法：找不到返回 null（或 Optional<T>）
  - 操作方法：前置条件不满足时抛 IllegalStateException，参数非法抛 IllegalArgumentException

  10. DeviceAdapter 接口设计过于耦合

  DeviceAdapter.parseStatusMessage(Object rawMessage) 参数是 Object，这意味着 MQTT 适配器传 MqttMessage，TCP 适配器传
  byte[]，调用方需要知道具体类型才能调用。适配器的目的是屏蔽协议差异，但这个接口反而暴露了差异。

  修订建议：
  - parseStatusMessage 不应出现在公共接口中，它是适配器内部的协议解析逻辑
  - 公共接口应只暴露业务语义方法：sendCommand、getVendor、getProtocolType、连接管理                                                            
  - 协议解析由各适配器内部的 MessageHandler 完成，解析后统一回调 EquipmentService.updateDeviceStatus()
                                                                                                                                               
  11. 两个阶段三                                                                                                                               
                                                                                                                                               
  集成开发总计划.md 第六节有两个"阶段三"——一个是"合规竞争力线（4周~6周）"，另一个是"集成验收（持续）"。标题重复。                              
                  
  修订建议：将"集成验收"改为"阶段四"或"持续验收"。                                                                                             
                  
  12. dms-masterdata 的 SchemeCreateRequest 缺少新增字段

  评审后 md_decoct_scheme 新增了 trace_code、alarm_high_temp、alarm_low_temp 三个字段，但 SchemeCreateRequest DTO 中没有包含这些字段。

  修订建议：SchemeCreateRequest 和 SchemeUpdateRequest 补充这三个字段。

  13. 心跳超时与温度上报代心跳的关系未明确

  dms-equipment 第 6.3                                                                                                                         
  节说"替代方案：若设备有温度上报，可用温度上报时间代替心跳时间判断在线状态"，但没有说明这两种方案如何选择、是否共存、优先级如何。
                                                                                                                                               
  修订建议：明确为"温度上报时同步更新 last_heartbeat"，这样心跳检测逻辑不需要改，温度上报自然延长在线判定。一句话就够，不需要两套方案。

  四、低危问题（建议改进）

  14. BaseEntity 用 Date 而非 LocalDateTime

  BaseEntity 中 createdAt/updatedAt 使用 java.util.Date。既然计划迁移到 JDK 17，建议从现在开始用 LocalDateTime，避免时区问题和后续迁移成本。   
   
  15. InspectionResult 的 result 字段用中文字符串                                                                                              
                  
  质检结果用 "通过"/"让步放行"/"返工"/"报废" 中文字符串做 switch-case 匹配，容易因空格、编码等问题导致匹配失败。                               
   
  修订建议：定义 InspectionResultType 枚举（PASS/CONCESSION/REWORK/SCRAP），SPI 接口参数和数据库存储统一用枚举名。                             
                  
  16. dms-print 的 prt_record 缺少 operator_id                                                                                                 
                  
  打印执行记录没有记录是谁触发的打印/重试，审计追溯时无法定位操作人。

  17. dms-analytics 视图中 TIMESTAMPDIFF 是 MySQL 函数                                                                                         
   
  ops_equipment_utilization 视图使用了 TIMESTAMPDIFF，这是 MySQL 特有函数，SQLite 不支持。既然开发环境用 SQLite，这个视图在开发环境无法创建。  
                  
  修订建议：视图 DDL 需要提供 SQLite 和 MySQL 两个版本，或者在 Flyway 中用条件脚本区分。

  18. 缺少 TaskService SPI 定义

  dms-production 是核心模块，但 dms-common 中没有定义 TaskService 或 ProductionService SPI。当前 dms-print 和 dms-quality                      
  如果需要反查任务信息（比如打印时需要处方号、患者名），没有合法途径获取。
