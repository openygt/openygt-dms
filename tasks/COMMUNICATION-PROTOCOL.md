## 二、沟通方式

### 2.1 文件矩阵

每位成员在 `docs/tasks/` 目录下维护两个文件:

| 成员 | 任务单 (架构师→成员) | 回复文件 (成员→架构师) |
|------|---------------------|----------------------|
| kimi01 | `kimi01-test-verification.md` | `kimi01-reply.md` |
| kimi02 | `kimi02-fix-compilation-and-status.md` | `kimi02-reply.md` |
| kimi03 | `kimi03-frontend-simulator-sync.md` | `kimi03-reply.md` |
| kimi04 | `kimi04-device-status-sync.md` | `kimi04-reply.md` |

### 2.2 更新规则

- **成员更新**: 完成阶段性工作后，在 `kimi0X-reply.md` 追加进度
- **架构师回复**: 直接在成员 reply 文件末尾追加 `## 架构师回复` 段落
- **禁止行为**: 不得删除他人内容，不得修改任务单文件

## 四、文档变更监控机制（三层保障）

> 目标：确保架构师和协调员**不遗漏任何成员更新**

### 4.1 第一层：后台 Watchdog（自动）

```bash
# 启动方式（kimi03 负责在服务器启动时执行）
cd docs/tasks && nohup bash .watchdog.sh > .watchdog.log 2>&1 &
```

- 每 **30 秒**轮询 `docs/tasks/*.md`
- 发现变更时，自动写入 `.watchdog.log`
- 同时追加到 **`pending-review.md`** 的「未读变更」表格

### 4.2 第二层：Pending Review 清单（架构师入口）

**架构师每次会话开始时，优先阅读此文件：**

```bash
cat docs/tasks/pending-review.md
```

- 「未读变更」表格由 watchdog 自动填充
- 架构师审阅后**手动清空表格**（保留表头），并追加到「审阅记录」
- 若 pending-review.md 中「未读变更」为空 → 说明无新动态

### 4.3 第三层：手动巡检（kimi03 每日）

```bash
# 每日至少执行一次
bash docs/tasks/check-updates.sh
```

输出示例：
```
[kimi01] 最后更新: 2026-04-25 01:00:25 | 大小: 309B
[kimi02] 最后更新: 2026-04-25 01:00:27 | 大小: 324B  ⚠️  最近5分钟内有更新！
```

### 4.4 汇报触发条件（kimi03 负责）

| 条件 | 动作 |
|------|------|
| `pending-review.md` 出现未读变更 | kimi03 确认并提醒架构师 |
| P0 任务延迟超过约定时间 | 立即升级汇报 |
| 成员提出阻塞问题 | 立即汇报架构师 |
| 全部成员标记完成 | 组织联调验证 |

### 4.5 汇报格式

```
## 📋 巡检汇报 YYYY-MM-DD HH:MM

### 成员状态
| 成员 | 状态 | 关键进展 |

### 阻塞与风险
- [ ] 无阻塞
- [x] 有阻塞: 说明...

### 需要架构师决策
1. ...
```

## 五、成员自主决策边界（关键！禁止等命令）

> 机制健康的标志：**成员知道自己该做什么，不需要架构师逐个发令。**

### 5.1 成员可自主决策的事项（无需等架构师）

| 场景 | 自主行动 |
|------|---------|
| 当前 Sprint 任务已完成 | 立即按「任务流转表」进入下一步，更新 reply 状态 |
| 发现本模块内的 bug | 直接修复，修复后更新 reply，不需要架构师批准 |
| 需要调用其他模块的已有接口 | 直接使用，有问题再上报 |
| 测试用例设计、Mock 策略调整 | 自主决定，完成后汇报结果 |
| 代码重构（不影响接口契约） | 自主决定，保证测试通过即可 |

### 5.2 必须上报架构师的事项

| 场景 | 上报方式 |
|------|---------|
| 需要修改其他成员负责的代码 | 在对方 reply 中留言，抄送架构师 |
| 接口契约变更（URL / 参数 / 返回值） | 立即在本文档「问题与疑问」中上报 |
| 发现 P0 级阻塞（编译失败 / 核心流程中断） | 立即在本文档「问题与疑问」中标注 |
| 对任务优先级有异议 | 在本文档中提出，架构师 30 分钟内响应 |
| 需要跨 Sprint 调整排期 | 必须经架构师批准 |

### 5.3 任务自动流转表

```
完成概设 → 自动进入详设（无需等架构师发令）
完成详设 → 提交审核，同时可开始环境准备
详设审核通过 → 自动进入开发
开发完成 + mvn test 通过 → 自动进入自验
自验通过 → 更新 reply 为「已完成」，等待联调触发
联调中发现本模块 bug → 自动进入修复
```

**核心原则：成员是任务的 owner，不是架构师的执行器。**

## 六、阻塞升级规则

1. **P0 任务优先**: kimi02 的编译修复是全局阻塞，任何成员发现其延迟应立即汇报
2. **依赖等待**: kimi03 前端修改依赖 kimi02 状态名统一，若 kimi02 未完成，kimi03 可先行代码修改但标记"待联调"
3. **跨模块冲突**: 若两名成员修改同一文件，先完成者通知协调员，协调员通知后完成者做 rebase/合并
