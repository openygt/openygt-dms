## 1. 总体架构

系统采用“模块化单体”架构：
- 后端为 Maven 多模块 Spring Boot 单体应用。
- 前端为 Vue3 + Vite 单页应用。
- 数据层使用 MyBatis-Plus。
- 外部依赖包括 MySQL、Redis、MQTT Broker。

当前部署模型为单进程单服务，不属于微服务架构。

## 4. 模块依赖原则

设计原则：
- `dms-app` 聚合所有业务模块。
- 各业务模块优先依赖 `dms-common`。
- 跨模块调用通过 `dms-common` 中的 SPI 接口完成。

当前可识别的跨模块契约包括：
- `EquipmentService`
- `PrintService`
- `QualityService`
- `ProductionQueryService`
- `SysConfigService`

## 5. 逻辑分层

后端采用典型分层：
- Controller 层：对外提供 REST 接口
- Service 层：业务编排与事务控制
- Mapper 层：数据库访问
- Entity/DTO 层：数据对象

特点：
- 生产主流程状态机集中在 `TaskServiceImpl`。
- 设备平台能力集中在 `EquipmentServiceImpl` 与设备服务实现。
- 前端以页面视图直连 REST API，未引入复杂 BFF 层。

## 6. 核心业务架构

### 6.1 生产状态机

主状态链路：
- 待泡药
- 泡药中
- 待煎药
- 煎药中
- 待出液
- 出液中
- 待包装
- 包装中
- 待贴标
- 待质检
- 待交接
- 已部分完成
- 已完成
- 已报废

特征：
- 每次状态变更都写入历史。
- 关键阶段写入步骤日志。
- 设备占用与释放纳入主流程。

### 6.2 设备接入架构

当前设计分两层：

平台层：
- 设备建档
- 设备状态更新
- 温度与告警
- 心跳离线
- MQTT 接收

适配层：
- `DeviceAdapter`
- `AbstractMqttAdapter`
- `AbstractTcpBinaryAdapter`
- `AdapterRegistry`

结论：
- 平台层已落地。
- 厂商协议层为半落地架构，需继续实现具体适配器。

### 6.3 打印架构

当前打印架构由以下对象构成：
- `PrintTask`
- `PrintRecord`
- `PrintService`

当前执行模型：
- 提交任务
- 校验打印机空闲
- 同步模拟打印完成
- 记录执行成功

限制：
- 没有真实驱动层。
- 没有异步消费器。
- 没有设备回执协议。

### 6.4 质量架构

质量模块只负责：
- 保存质检记录
- 返回质检结果

生产状态流转仍由生产模块主导。这一设计符合“主流程归生产域、质量结果归质量域”的边界划分。

## 7. 前端架构

当前前端结构：
- `router`：静态路由定义
- `stores/user.ts`：登录态、菜单、权限存储
- `views/*`：按业务域划分页面
- `components/Layout.vue`：主布局

当前问题：
- 菜单是静态渲染，不是后端菜单树驱动。
- 页面权限依赖 token 中的 `permissions`，但后端 token 未提供此字段。

### 8.1 表域划分

- `sys_*`

- `eq_*`

- `inv_*`

打印：
- `prt_*`

分析：
- 统计主要来自查询聚合，`ops_*` 体系尚未真正铺开

### 8.2 数据库迁移架构

当前实现：
- 通过 `DatabaseInitConfig` 在启动时执行脚本数组。
- 对 MySQL 采用 SQLite SQL 文本转换。

判断：
- 该机制可用于早期快速迭代。
- 不适合作为长期正式迁移体系。

建议目标架构：
- 使用 Flyway 标准版本迁移。
- 显式基线、回滚、校验。

## 9. 安全架构

### 9.1 当前机制

- 采用 JWT 认证。
- 使用 Spring MVC Interceptor 做认证与权限拦截。
- 登录成功后 token 中包含角色信息。

### 9.2 当前问题

- 拦截范围与 API 前缀不完全一致。
- 权限拦截实际按角色判断。
- JWT 密钥硬编码。

### 9.3 目标改进

- 统一接口前缀。
- 统一角色与权限码模型。
- 使用配置化密钥与密钥轮换。
- 补接口级审计与安全测试。

## 10. 部署架构

推荐当前部署方式：
- 前端静态资源由独立 Web Server 或打包后统一发布。
- 后端单 Jar 部署。
- 连接 MySQL、Redis、EMQX。

当前不建议：
- 直接拆分微服务。

原因：
- 当前复杂度主要在业务完善，不在服务拆分。
- 权限、迁移、设备协议尚未稳定，先做微服务会放大复杂度。
