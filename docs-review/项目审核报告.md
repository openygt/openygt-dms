# OpenYGT 煎药室管理系统项目审核报告

| 版本 | V1.0 |
|------|------|
| 日期 | 2026-04-27 |
| 审核范围 | 代码实现、现有文档、构建与测试基线 |
| 审核基准 | 以仓库当前代码为准，不采信未落地规划 |

## 1. 审核结论

项目当前处于“可运行的模块化单体 MVP / Beta”阶段，不是“与代码完全对齐的成熟基线系统”。

已具备的能力：
- 多模块单体后端与 Vue3 前端骨架完整。
- 处方建单、生产任务状态流转、设备管理、打印、质检、用户/RBAC、医院/方案、仪表盘等主链路已落地。
- Maven 编译可通过。

主要问题：
- 认证鉴权边界不一致，存在接口绕过统一鉴权的风险。
- RBAC 后端与前端权限模型不一致，部分页面/能力在前端不可用或依赖静态菜单。
- 数据库迁移机制不规范，存在版本漂移和新迁移未执行风险。
- 若干模块被旧文档标记为“已实现”，实际只是骨架或简化实现。
- 设备接入、打印、分析报表仍以模拟/半成品为主，距离生产级仍有差距。

建议结论：
- 可以作为内部联调与受控试运行版本。
- 不建议在未完成安全、迁移、权限一致性整改前作为正式生产基线。

## 2. 高优先级发现

### 2.1 库存接口绕过统一认证与权限拦截

证据：
- [WebMvcConfig.java](/data2/docker/decoction/openygt-dms-a/dms-app/src/main/java/cn/org/openygt/config/WebMvcConfig.java:19) 仅拦截 `/api/v1/**`。
- [ConsumeRecordController.java](/data2/docker/decoction/openygt-dms-a/dms-app/src/main/java/cn/org/openygt/controller/inventory/ConsumeRecordController.java:16) 暴露的是 `/api/inventory/consume`。

影响：
- 消耗流水写入与查询接口不受统一 JWT 认证和权限拦截保护。
- 该问题属于明显安全边界缺口。

建议：
- 统一 API 前缀到 `/api/v1/**`。
- 或调整拦截器覆盖范围并补充细粒度权限注解。

### 2.2 权限模型前后端不一致，功能可达性异常

证据：
- 前端路由按权限字符串控制页面访问，例如 [router/index.ts](/data2/docker/decoction/openygt-dms-a/frontend/src/router/index.ts:15) 中使用 `prod:task:list`、`sys:user:list` 等。
- 前端登录后从 token 中读取 `permissions`，但 [user.ts](/data2/docker/decoction/openygt-dms-a/frontend/src/stores/user.ts:39) 实际只会得到空值。
- RBAC 登录接口 [RbacController.java](/data2/docker/decoction/openygt-dms-a/dms-rbac/src/main/java/cn/org/openygt/rbac/controller/RbacController.java:138) 仅把 `roles` 写入 token。
- 权限拦截器 [PermissionInterceptor.java](/data2/docker/decoction/openygt-dms-a/dms-rbac/src/main/java/cn/org/openygt/rbac/interceptor/PermissionInterceptor.java:33) 也是按角色字符串匹配，而不是权限码匹配。

影响：
- 前端页面守卫与后端授权语义不一致。
- 菜单和页面可能因为拿不到 `permissions` 被强制跳回看板。
- 系统对“角色”和“权限”的边界定义不清，后续扩展会持续出问题。

建议：
- 明确采用“角色 + 权限码”双层模型。
- JWT 中增加权限码 claims，或前端单独拉取权限列表。
- 后端注解名称和语义改为真实权限校验，而非角色校验。

### 2.3 数据库迁移机制存在版本漂移风险

证据：
- 启动迁移脚本列表固定写死在 [DatabaseInitConfig.java](/data2/docker/decoction/openygt-dms-a/dms-app/src/main/java/cn/org/openygt/config/DatabaseInitConfig.java:26)，只执行到 `V16__fix_qt_inspection_columns.sql`。
- 实际 `db/migration` 目录中已有 `V17`、`V18`，以及重复版本号 `V15__sys_log_updated_at.sql`、`V16__inv_stock_log.sql`。

影响：
- 新增迁移可能永远不会执行。
- 重复版本号会造成文档、脚本、数据库状态难以对账。
- 当前机制不是标准 Flyway/Liquibase，用手工数组维护成本高且容易漏。

建议：
- 立即改用 Flyway 标准迁移。
- 清理重复版本号，统一一条版本序列。
- 增加数据库版本基线文档和回滚策略。

### 2.4 分析报表被文档高估，实际仍是半成品

证据：
- [CapacityReportServiceImpl.java](/data2/docker/decoction/openygt-dms-a/dms-analytics/src/main/java/cn/org/openygt/analytics/service/impl/CapacityReportServiceImpl.java:13) 明确标注为空实现骨架。
- 医院筛选仅留 TODO。
- Dashboard 中质检通过率直接写死为 100%，见 [DashboardServiceImpl.java](/data2/docker/decoction/openygt-dms-a/dms-analytics/src/main/java/cn/org/openygt/analytics/service/impl/DashboardServiceImpl.java:40)。

影响：
- 当前 analytics 适合作为演示看板，不适合作为经营决策依据。

建议：
- 将 analytics 在需求和产品文档中降级为“基础统计/演示态”。
- 补真实聚合 SQL、时间窗口、医院维度、异常率定义。

### 2.5 打印中心是同步模拟实现，不是真实打印编排

证据：
- [PrintServiceImpl.java](/data2/docker/decoction/openygt-dms-a/dms-print/src/main/java/cn/org/openygt/print/service/PrintServiceImpl.java:166) 中“执行打印”只是同步置为完成、记录成功。
- 未见真实打印机驱动、任务异步消费、失败回执、设备协议交互。

影响：
- 业务上可跑通“打印流程字段”，但不等于真实打印集成完成。

建议：
- 文档中应定义为“打印任务管理与模拟执行已实现”。
- 若要生产化，需增加设备适配、异步队列、失败分类、补打审计。

## 3. 中优先级发现

### 3.1 JWT 密钥硬编码

证据：
- [JwtUtil.java](/data2/docker/decoction/openygt-dms-a/dms-common/src/main/java/cn/org/openygt/common/util/JwtUtil.java:51) 使用固定 `SECRET`，未真正从配置注入。

影响：
- 生产环境密钥不可轮换，不符合安全基线。

建议：
- 改为环境变量或配置中心注入，并支持密钥轮换。

### 3.2 前端菜单并未真正按后端返回菜单树渲染

证据：
- [Layout.vue](/data2/docker/decoction/openygt-dms-a/frontend/src/components/Layout.vue:1) 使用静态菜单。
- `userStore.fetchMenus()` 虽请求菜单树，但结果未驱动布局渲染。

影响：
- RBAC 菜单管理的业务价值未真正闭环。

建议：
- 菜单树与路由、权限、可见性统一由后端或前端配置驱动。

### 3.3 设备接入以通用 MQTT + 自动创建设备为主，真实厂商适配尚未落地

证据：
- 已有 `DeviceAdapter` 抽象和 MQTT/TCP 基类。
- 但未见具体厂商适配器落地到生产链路。

影响：
- 系统对真实设备厂商协议的适配深度不足。

建议：
- 明确“平台级设备接入框架已实现，厂商级适配未完成”的阶段状态。

### 3.4 测试覆盖不均衡

现象：
- 各模块已有一定测试文件。
- 但从代码结构看，更偏向服务层和控制器基本用例，缺少跨模块集成、权限、安全、迁移回归验证。

建议：
- 增加以下自动化测试：
- 认证与授权回归测试。
- 迁移脚本升级测试。
- 生产主流程端到端测试。
- MQTT 设备消息驱动测试。

## 4. 架构评审意见

优点：
- 模块边界总体清晰，`dms-common` 抽象了跨模块 SPI。
- 采用模块化单体适合当前团队规模和业务阶段。
- 生产任务状态机已形成系统主骨架，能承接后续设备与质量扩展。

不足：
- 接口风格、状态枚举、权限模型尚未完全收敛。
- 数据迁移、配置管理、安全能力仍偏“开发态”。
- 前端与后端的“权限/菜单/API 边界”没有统一设计。

建议的近期整改顺序：
1. 统一 API 前缀、认证、授权模型。
2. 改造数据库迁移为 Flyway 标准方案。
3. 把前端菜单、权限、路由从静态拼装改为统一模型。
4. 补齐 analytics 与 print 的真实业务能力定义。
5. 推进至少一家真实设备厂商适配联调。
